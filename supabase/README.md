# Database setup (Supabase)

## 1. Create the project
1. Create a project at https://supabase.com (the free tier is fine). Pick the region closest to the
   Philippines (e.g. Singapore).
2. **Project Settings → API**: copy the **Project URL** and the **anon public** key. These go in the
   frontend `.env` in Phase 3. **Never** put the `service_role` key in the frontend.

## 2. Apply the migrations
Open **SQL Editor** and run each file **in order**, one at a time:

| # | File | What it does |
|---|------|--------------|
| 1 | `migrations/0001_extensions_enums.sql` | pg_trgm, enum types, reference-number sequences |
| 2 | `migrations/0002_tables.sql` | All 13 tables, constraints, indexes |
| 3 | `migrations/0003_functions_triggers.sql` | Role helpers, signup trigger, validation, history, notifications |
| 4 | `migrations/0004_rls_policies.sql` | Column grants + Row Level Security on every table |
| 5 | `migrations/0005_rpc.sql` | RPCs for reports, claims, moderation, users, statistics |
| 6 | `migrations/0006_storage.sql` | `item-images`, `claim-evidence` (private), `avatars` buckets + policies |
| 7 | `migrations/0007_reference_data.sql` | Settings, 9 categories, 12 campuses, common locations (safe to re-run) |

**Shortcut:** `supabase/setup_all.sql` contains all 7 migrations in order (generated by
`npm run build:sql`). On a new, empty project, paste it into one SQL editor query and run it once.

With the Supabase CLI instead: `npx supabase link --project-ref <ref>` then `npx supabase db push`.

## 3. Verify (recommended)
Run `tests/rls_test.sql` in the SQL editor. It creates throwaway users inside a transaction, runs
112 security/workflow checks, and **rolls everything back**. The last row must read
`ALL TESTS PASSED`; a failure shows an error starting with `TEST FAILED:`.

> If your project refuses `insert into auth.users` from the SQL editor, run the same checks
> locally instead (next section).

Offline check, no Supabase needed:
```bash
npm run test:db
```

## 4. Authentication settings
**Authentication → URL Configuration**
- Site URL: `http://localhost:5173` for development (your deployed URL in production)
- Redirect URLs: add `http://localhost:5173/reset-password` and `http://localhost:5173/login`
  (plus the production equivalents)

**Authentication → Providers → Email**
- Email provider: enabled
- Confirm email: **on** for production. For quick local testing you may turn it off.
- Minimum password length: 8

The default Supabase mailer is rate-limited (a few emails per hour). Configure custom SMTP before
real use.

## 5. Create the first super administrator
1. Register in the app with your `@cvsu.edu.ph` email.
2. Edit the email in `seed.sql` and run it in the SQL editor.
3. Sign out and back in. You now have the admin pages, and can promote other admins from
   **Admin → Users**.

## Design notes
- **Only `@cvsu.edu.ph` can register** (`system_settings.allowed_email_domains`). For testing with
  personal emails, set it to `[]` (see the commented line in `seed.sql`). Never do that in production.
- **Status columns cannot be written by clients.** Every status change goes through an RPC that
  checks the caller's role, records history, writes the audit log and sends notifications in one
  transaction.
- **Sensitive details live in `lost_item_private` / `found_item_private`**, readable only by the
  reporter and admins. Claims are readable only by the claimant and admins — not by the finder.
- **Function execute rights are deny-by-default** (end of `0005_rpc.sql`). If you add a function
  that the frontend must call, add a `grant execute … to authenticated` for it.
